# 経路コストの実験(2026-09-29)

最短走行の経路生成(`MainTask::path_run()` の「右」)と、探索のサブゴール選び(`Adachi::update()`)を、
重みパターンの値・段数・方式を変えて比べたときの道具一式。ファームのソースは読むだけで、書き換えた写しは
`build.py` がこのフォルダの中に作る(`.gitignore` 済み)。ファームには何も入れていない。

迷路は `tools/param_tuner/maze_data`・`profile`・`maze_logs` から重複(壁の違い 3 枚以下)を除いた 21 本
(`px/ds.py`)、走行モードは run_prf の 1 / 3 / 5 / 11 / 16(`px/ev.py` の `EXECS`)= 105 ケース。

**その後(同日)**: ここの結果をもとに、ファームへ `TimePathPlanner`(`src/action/time_path_planner.cpp`)を入れ、
`calc_goal_time()` に最後の直線を足した。このフォルダは検討時点の記録で、数字は変更前のファームに対するもの。
いまのファームでは `calc_goal_time()` が最後の直線を含むので、`opt.py` の「ファームと同じ数え方」
(`count_final: false`)の比較は合わなくなる。ファームの探索の確認は `../check_time_path.py` を使う。

探索まわりのソース(`adachi.cpp` / `adachi.hpp` / `logic.cpp` / `logic.hpp` / `search_main.cpp`)は、検討時点の
写しを `frozen/` に置いてあり、`build.py` はそれを書き換えて使う(ファームのほうは、この結果を受けて
サブゴールの選び方を変えたため)。経路生成(`path_creator.cpp` ほか)はファームの今のソースを使う。

## 使い方

```bash
python3 px/build.py && python3 px2/build.py     # 先にファームを cmake configure しておく(ArduinoJson)
cd px
python3 verify.py        # 実験用ビルドが tools/path_sim/build/path_sim と同じ結果か
python3 rs.py 3000 1 a   # 重み 6 個を 3000 通り(約 8 分、rs_a.pkl)
python3 an.py a; python3 an2.py a
python3 t2.py            # 表にした重み / あとから安い値で直す版 / 分岐候補の幅
python3 phys.py          # 加速度とターン時間から作った 16 段の表
python3 opt.py           # タイム最小の探索と現行の比較(opt.pkl)
python3 opt2.py          # 速い版の確認と計算時間
python3 tr.py            # ファームの経路がタイム最小の探索の辺でなぞれるか
python3 se.py [名前…]    # 探索のサブゴールの選び方の比較(se.pkl に覚える。名前を渡すとそれだけやり直す)
python3 dpcost.py        # 探索の途中で呼んだときの計算量
```

## 何があるか

| ファイル | 中身 |
|---|---|
| `px/build.py` | 重みを外から入れられるようにした `logic.hpp` / `adachi.cpp` / `search_main.cpp` の写しを作ってビルド |
| `px/px_path.cpp` | 重みパターンをまとめて評価(1 パターンぶんの path_create → timebase_path_create) |
| `px2/build.py` | 上に加えて: 重みを 16 段の表に、あとから安い値で直す版、分岐候補の幅、素の経路の記録、探索へのフック |
| `px2/opt_core.hpp` | タイム最小の探索の試作(分かりやすさ優先) |
| `px2/opt_core2.hpp` | 同じ探索の速い版(整数の鍵・表引き・ハッシュ表・2 分ヒープ・残り時間の下限)。ファームへ持っていくならこちら |
| `px2/px_opt.cpp` | 上の 2 つを呼ぶコマンド。素の経路をファームの変換と `calc_goal_time` に通す確認も持つ |

## タイム最小の探索の考え方

経路を「直線 + ターン」の区間の列として、区間を辺にした最短経路問題を解く。辺の重みは `calc_goal_time()` の
1 区間ぶんと同じ計算(`seg_raw()` がその写し)。節点は「ターンを終えた位置・向き・直進か斜めか・出口速度・
次の区間への約束」。約束は `calc_goal_time()` の先読み(次が 直線 > 0 + Large / Orval なら速いターン)を
辺の重みへ入れるためのもの。辺の作り方は `convert_large_path()` / `diagonalPath()` の規則の写し:

- ターン 1 個 = Large、同じ向き 2 個 = Orval
- 向きが交互に続く組 = 斜め。入口は Dia45(最初が同じ向き 2 個なら Dia135)、出口も同じ。途中の同じ向き 2 個は Dia90
- 同じ向き 3 個(その場で 270° 回る形)は Normal が残るので対象外

求めた経路は素の経路(path_create が作る形)に直して、ファームの変換と `calc_goal_time()` に通し、探索の
タイムと同じになることを確かめている(105 ケースすべて一致)。ファームの 5 パターンが出した経路 525 本も
この探索の辺でなぞれて同じタイムになる。

## 実験 4: 探索のサブゴールをタイム最小の経路から取る(2026-09-29)

「探索時間を削ると取りこぼしが増える」関係そのものをなくせるかを見た。`px2/search_hooks.hpp` と
`px/se.py`(`sub_dp: 6`)。サブゴールは「未知の壁を無いものとしたタイム最小の経路の上の未知区画」だけ。

- 覚えた経路は、その上に壁が見つかるまで使い続ける。新しく分かるのは壁だけなので、ほかの経路が
  速くなることは無く、塞がれない限り最小のまま(計算し直しは 1 探索あたり 3 モードで 65〜105 回)。
- 探すのは「既知の区画だけで作れる最小タイムより速い経路」だけ(上限 + 残り時間の下限)。
- `dp_lag` 秒後に結果が届く想定(機体では走りながら裏で計算する)。届くまでは前の経路の未知区画を使う。
- `dp_collapse`: 節点を「位置・向き・直進か斜めか」にまとめた軽い版(既知の迷路では厳密な最小との差
  平均 +0.04 %、105 件中 99 件は同じ経路)。

| サブゴールの選び方 | 探索時間の合計 | 取りこぼし | 計算し直し 1 回(PC) |
|---|---|---|---|
| パターン 1 だけ(以前) | 4886 s | 25 / 105 | — |
| パターン 1 + 予備 4→3→2 | 5244 s | 15 / 105 | — |
| タイム最小・厳密・遅れなし | 4563 s | 0 / 105 | 平均 60 ms、節点最大 3.9 万 |
| タイム最小・まとめた版・2 秒遅れ | 4601 s | 1 / 105(5 ms) | 平均 9 ms、最大 43 ms、節点最大 8912 |
| 同 4 秒遅れ | 4703 s | 2 / 105、帰還できず 1 | |
| 同 8 秒遅れ | 4829 s | 5 / 105、帰還できず 2 | |

だめだった案: 節点の上限を 4096 にして粗くする(取りこぼし 23 件)、下限を 1.5〜5 倍に見て粗く探し帰還時に
厳密に確かめる(出直しが増えて 5017 s 以上)、モード 1 つだけ(ほかのモードで取りこぼし 13 件)。

## 実験 5: 重みパターンを複数使い、経路が塞がれたときだけ表を作り直す(2026-09-29)

「パターンの表を同時に展開できないか」(1 回の移動あたりの計算を増やさずに複数パターンを使いたい)を
受けて。`sub_dp: 9`(`px2/search_hooks.hpp` の `pattern_lazy`)と `px/sub.py`(組の総当たり)。

- 表の同時展開そのものは効かない: 広げる順番がパターンごとの歩数で決まるので、1 回の展開で複数の表は
  作れない(順番を共通にすると表の中身が変わる)。表もパターンの数だけ同時に持つことになる。
- 代わりに、パターンごとに経路(`searchGoalPosition` が歩いた区画)を覚え、その上に壁が見つかったときだけ
  そのパターンの表を作り直す。サブゴールは覚えた経路の上の未知区画(前回までのものは持ち越さない)。
- 毎回作り直す版と結果はほぼ同じ(1+2+3+4: 毎回 4843 s / 9 件、塞がれたときだけ 4819 s / 9 件)。

| 組 | 探索時間 | 取りこぼし | 作り直し(枚/移動) |
|---|---|---|---|
| パターン 1 だけ・持ち越す(以前のファーム) | 4886 s | 25 / 105(1742 ms) | 1(毎回) |
| パターン 1 + 予備 4→3→2(いまのファーム) | 5244 s | 15 / 105(472 ms) | 1 + 予備 |
| 2+4 | 4794 s | 9 / 105(175 ms) | 0.21(0 枚 84 % / 1 枚 10 % / 2 枚 6 %) |
| 2+4、1 回の移動で 1 枚まで | 4820 s | 9 / 105(175 ms) | 0.18(0 枚 82 % / 1 枚 18 %) |
| 2+3+4 | 4753 s | 9 / 105(175 ms) | 0.34 |
| 1+2+4 | 4829 s | 8 / 105(145 ms) | 0.28 |
| 3+4 | 4710 s | 16 / 105(254 ms) | 0.22 |
| (参考)タイム最小の経路・2 秒遅れ | 4601 s | 1 / 105(5 ms) | 別の計算 |

パターンの組では取りこぼし 8 件より下へは行かない(31 通りすべて試した。`sub.py`)。

**その後(同日)**: 「2+4、1 回の移動で 1 枚まで」を一度ファームへ入れたが、取り消した。合計では得でも
迷路ごとの差が大きく(探索 −47〜+97 s、最短走行が速くなるのは 21 本中 4 本、2016 年は +97 s で改善なし)、
探索中に動く部分へ切り替えを足すほどのリターンではない、という判断。ファームの探索は元のまま
(重みパターン 1 を毎回)。`px/ref_search.json` は、この実験の迷路ごとの結果(探索時間・判断の回数・
探索後の地図での最短走行のタイム)。

## 実験 6: 探索中の update() まわりの処理時間(2026-09-29)

`emu/`。ファームの `src/search/logic.cpp` を、ファームと同じコンパイラ・同じオプション(Cortex-M33、-O3)で
ビルドし、CPU エミュレータ(Unicorn)の上で動かして命令数を数える。状態は、ホストの探索シミュレータが
ゴール後の `update()` の直前に残したもの(地図・自己位置・サブゴール)。機体での実測ではない。

```bash
cd emu && pip install --target pylib unicorn && ./build.sh && python3 run.py
python3 emu.py bench_orig.elf snap_japan2025_final.bin --count 12 --stride 60 --prof   # 関数ごとの内訳
```

| 迷路 | update() の中身(表づくり + 経路) | exec() の歩数マップ |
|---|---|---|
| japan2025_final | 137 万 → 59 万命令(−57 %) | 11.2 万 → 1.7 万(−84 %) |
| 32MM2019HX | 119 万 → 54 万(−55 %) | 9.2 万 → 1.4 万(−85 %) |
| japan2019hes | 157 万 → 62 万(−60 %) | 8.8 万 → 1.4 万(−84 %) |

- 左がファームそのまま、右が `emu/opt.cpp` の試作。試作は結果を変えない(表・サブゴール・歩数マップが
  全状態で一致)。やったのは、区画の範囲確認(`valid_map_list_idx`)を 1 か所にまとめる、向きごとの if の
  連鎖を表引きにする、小さい関数の呼び出しをやめる、サブゴールの期限切れをサブゴールの数だけ回す、の 4 つ。
- ファームそのままの内訳: `updateVectorMap` 本体 35 %、`valid_map_list_idx` 28 %(1 回の update で約 2.8 万回
  呼ばれる)、`addVector` / `getDistV` / `existWall` / `get_map_val` / `haveVectorLv` / `getVector` が各 3〜5 %。
  小さい関数にはどれも `noinline` が付いていて、毎回関数呼び出しになっている。
- ゴール後の `update()` のうち、地図が前回と同じ(既知の区画を走っているだけ)のものが 36〜59 %。
  このときは表を作り直さなくても同じ結果になる(未実装・未検証)。
- 命令数から時間への換算は未確認。機体で `update()` が約 20 ms という観測(直進の伸びから逆算)と
  137 万命令を突き合わせると、1 命令あたり約 2.2 サイクル。

## 注意

- `adachi.hpp` は隣の `logic.hpp` を読むので、`logic.hpp` にメンバーを足す実験では `adachi.hpp` の写しも
  `inc/` に置く(`px2/build.py`)。置かないと、その翻訳単位だけ元のクラス配置で `set_param()` が展開され、
  重みが切り替わらない(一度これで探索の比較を取り違えた)。
- `calc_goal_time()` は最後の直線(最後のターン〜ゴール)を足していない。`count_final: false` がファームと
  同じ数え方、`true` が足した値。
