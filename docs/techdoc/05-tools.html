CHAPTER 5

開発環境・ツール

調整はブラウザの Param Console から、解析は走行ログに対する Python スクリプトで行います。制御則の変更は「ログから実効ゲインを逆算できる」ことを前提に設計しています。

5.1 Param Console (Web)

tools/param_tuner/webapp/ の Next.js アプリ。旧来の受信 (rx_term.js) と送信 (tx_term.js) を 1 本の永続シリアル接続に統合し、./param_console.sh で起動して http://localhost:3000 を開きます。

  • 自動接続: ttyACM* を 200 ms 間隔でポーリングし、見つかり次第接続。切断後も再検出。
  • コンソール: 受信をリアルタイム表示。画面クリアのエスケープを検知して自動リセット。
  • パラメータ送信: profile/hf/ と system.yaml / hardware.yaml を一覧し、個別送信・全送信・検索・その場の YAML 編集 (CodeMirror、Ctrl+S 保存)。
  • テストテンプレート: system.yaml の test: ブロックの特定キー (v_max / accl / dist / suction_active / file_idx / sla_type など) と mode を、コメントを壊さずに書き換える。よく変える値はワンクリックで即時反映。
  • ログプロット: 受信した CSV から走行軌跡を描画 (状態ごとに色分け、壁センサー検出点、90 mm グリッド)。旋回出口の残差表やチャートプリセットを持つ詳細ビューと、PlotJuggler への連携ボタン。
  • ダンプ受信の頑健化: バイナリヘッダーの欠落やバーストによる破損を検出し、破損時は破棄してトーストで再試行を促す。

レイアウトはプロット最優先で、表は右ペイン、操作はヘッダーに寄せています。

5.2 ログ可視化

  • plot_gui.py: tools/param_tuner/logs/ の CSV を選び、位置・センサー軌跡を Tk で表示。PlotJuggler (ROS 2 Jazzy の apt 版) を起動・終了するボタンつき。snap 版は AppArmor の制約で pkill が効かないため apt 版を使います。
  • ログの CSV は 1 kHz × 最大 60 秒。反復試行のログは turn_log/NN/ に段階ごとに保存し、n ≥ 4 の比較に使います。

5.3 解析スクリプト (tools/param_tuner/)

スクリプト目的方法
ff_check.py直進 FF (Mass / 摩擦 / Ke) の同定実際に出た電圧を (accl, v) で回帰し、FF だけから作った電圧の係数と比較。ratio が 1 に近いほど FF が合っている
lat_check.py直進の横方向ループの符号確認壁 PD・角度 PID・Kanayama の各項の符号を突き合わせ。ki < angle_pid.p / S が安定条件
tread_check.py実効トレッドと左右タイヤ径差v_r − v_l = tread × w + (e_r − e_l) × v_c の最小二乗
enc_lut_fit.pyエンコーダ角度補正テーブル低速直進を複数本プールし、左右差とジャイロだけで 1〜8 次高調波を当てはめて 64 点に。--check でファームの適用確認
turn_exit_check.py旋回ごとの出口残差 (横ずれ・ヨー) と追従状態「旋回直後の duty_sen が大きい」は片壁 ×2 とヨー 0.96 mm/度で 3〜4 倍誇張されるため、出口残差そのもので判定
wall_off_edge_check.py壁切れ検出位置の数値評価ログの 45° 系列から検出位置とアンカーのずれを出す
vel_loop_margin.py速度ループの位相余裕離散 PID + トルク→電圧ゲイン + 遅れ 1.5 ms の開ループを周波数掃引
analyze_sensor_trough.py ほか柱谷・センサー落ち込み・状態遷移の切り出しモーション種別の区間内で極小点や遷移時刻を列挙
hf_series.py高頻度壁切れサンプルの復元4 kHz 相当のサブサンプル列を 1 kHz ログから展開 (ファーム側は試作ブランチ)

5.4 スラローム設計ツール

tools/slalom/ の Tk GUI (main.py) で、v / ang / rad / pow_n から角加速度の形状を積分 (RK) し、前後オフセット (front / back) を求めます。結果は result.yaml に出し、profile/hf/t_NNNN.yaml へ転記します。2.3 節の設計式で duty 予算と横 G を先に確認してから GUI で寸法を詰める流れです。

5.5 MATLAB / Simulink

tools/matlab_ws/ に、目標値 (位置・角度) と制約 (速度・加速度・角加速度) から指令値を計算するモデル (sim_mpc.slx / mpc_tgt_calc.slx) があります。init.m の test_mode で直進・スラローム (オリジナル加速 / 固定加速)・超信地・後退を切り替えてスコープで確認し、build_mpc_tgt_calc.m で Embedded Coder がコードを生成して gen_code_mpc/ に置きます。PID ブロックも同様に gen_code_pid/ / gen_code_simple_pid/ に生成しています。

生成コードの注意点: && と || の優先順位が曖昧な if 文が -Werror=parentheses で止まる (手で括弧を足す)、sign() が入力がちょうど 0 を跨ぐ瞬間だけ 0 を返す仕様で摩擦 FF がチャタリングする (直前値を保持して吸収)、pow(x, 0) が無条件に 1 を返す規約 (減速ソフトスタートの未配線バグの一因)。

5.6 ホスト側テスト

  • tests/dither_pwm_host/: DitherPwm のリング更新を DMA 読み位置のモデルとともにシミュレートし、遅延・guard・underrun を確認。
  • tests/pillar_trough_host/run.sh: 柱谷検知器に実走ログの CSV を全行再生し、発火位置と lag を出す。しきい値の検討は実機を走らせずにここで行います。

5.7 検証の作法

  • 制御変更の効果は単発比較ではなく n ≥ 4 の反復試行で判定する。ばらつきが 3σ で見込める場合は 1〜2 本で足りることもあるが、まずオフラインで当たりを付ける。
  • 「収束しない」と「duty が足りない」は別問題として切り分ける (平衡点が 0 か、飽和しているか)。
  • 壁切れの判定はしきい値ではなく形で行い、首振れとの分離は離脱の急峻さ・深さの数値で示す。
  • 失敗時の防御的コードは破棄だけで終わらせず、生データの保存と診断ログまで行う。
