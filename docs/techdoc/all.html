ExiaIgnis 技術資料

RP2350 (Raspberry Pi Pico 2) を使ったハーフサイズ・マイクロマウス ExiaIgnis の、機体構成と制御を中心にまとめた技術資料です。前作 Astraea シリーズ (ESP32-S3) のソフトウェア資産を引き継ぎつつ、MCU を RP2350 に変えて制御系・電装系を再構成しました。ファームウェアと調整ツールは GitHub の Naophis/ExiaIgnis で公開しています。

設計の要点

  • コアの完全分離。Core1 はセンシングと制御の IRQ だけを走らせ、Core0 が UI・パラメータ・USB・ログを受け持ちます。Core1 のホットコードはファイル単位で SRAM に配置し、フラッシュ (XIP) の遅延を制御ループから追い出しました。
  • モデルベースの前置き補償。走行の大部分はモーターモデル (逆起電力・抵抗・慣性・摩擦) によるフィードフォワードが担い、PID は残差だけを見ます。ゲインは走行ログの回帰で同定し、Python の検証スクリプトで裏を取る運用です。
  • CPU を介さない出力段。駆動 PWM は DMA が SRAM リングを永久再生する時間ディザ (DitherPwm) で 1 count 未満の duty を出し、吸引 ESC への DShot も PIO + DMA が自律送出します。Core1 が止まっても最後の指令が出続けます。
  • 壁切れは「値」ではなく「形」で判定。柱の谷を走行距離で正規化した 2 階微分 (曲率) で捉え、谷底位置をアンカーにして旋回位置を決めます。
  • 調整はブラウザから。YAML のパラメータ群を Web の Param Console からシリアル送信し、走行ログはその場で軌跡表示と PlotJuggler 連携ができます。

CHAPTER 1

機体構成

採用した部品と、その理由・困ったことを部位ごとにまとめます。値は 2026-09 時点のパラメータファイル (tools/param_tuner/profile/) と include/define.hpp に基づきます。

1.1 MCU: RP2350 (Raspberry Pi Pico 2)

項目内容
コアCortex-M33 ×2、150 MHz。Core0 = UI/USB/パラメータ/ログ、Core1 = センシング + 制御 (タイマー IRQ)
フラッシュQSPI 4 MB。末尾 256 KB を LittleFS にしてパラメータと迷路データを保存
PSRAMAPS6404L 8 MB を QMI の CS1 (GPIO0) に接続。走行ログ専用のバンプアロケータで使用
SRAM520 KB。Core1 のホットコードとデータを配置 (RAM 側 .data 約 223 KB、ヒープ約 266 KB)
PIO / DMAPIO1 + DMA で吸引 ESC への DShot を自律送出、PWM + DMA で駆動 duty の時間ディザ
USBUSB CDC のみ (UART 無効)。TinyUSB は Core0 固定のため printf は Core0 専用

採用理由: ESP32-S3 (Astraea) では FreeRTOS のタスク優先度と SPI/ADC ドライバのオーバーヘッドが 1 kHz 周期の乱れの原因になっていました。RP2350 はハードウェアアラームから直接 IRQ を受けられ、ADC も 1 変換あたり 2 µs で回せるので、OS なしでセンシングと制御を IRQ だけで組めます。DMA の ENDLESS 転送 (RP2350 で追加) が、後述の DitherPwm と DShot の「CPU 非関与」設計を可能にしました。

困ったこと: PSRAM の CE# (GPIO0) が Low に落ちない基板不良で一時ログが取れず、QSPI バスに残ったアドレスの残像が「形だけ正しいゴミ CSV」として出てきました。起動時に実書き込みテスト (psram_check::rw_test) を入れ、失敗時はログ機能を止めるようにしています (7 章参照)。

モータードライバ: MPQ6612A

2026-09-20 に MP6619L から換装し、直列インダクタも撤去しました。換装直後、400 mm/s 巡航に必要な duty が 4.3 % → 16.4 % に跳ね上がり、原因は抵抗ではなく減衰モードの違いでした。

IN1 / IN2MPQ6612A の出力
L / LCoast (Hi-Z)
H / LForward
L / HReverse
H / HBrake (両 LS-FET オン)。約 1 ms 続くと low-IQ brake へ

旧ドライバでは「片側 PWM・片側 0」が drive ↔ brake (slow decay) でしたが、MPQ6612A では drive ↔ coast (fast decay) になり、インダクタも無いので電流が不連続になって duty → トルクに約 15 % の不感帯が出ていました。MOTOR_DRIVE_SLOW_DECAY=1 で「駆動側 IN を H 固定、反対側 IN を反転 PWM」に変え、OFF 期間をブレーキ (モーター短絡) にすることで平均電圧が duty に線形になり、回生制動も効くようになりました。適用後の巡航 duty は 5.57 %、速度 I 項は +1.39 V → +0.07 V です。

ループ抵抗の実変化 (インダクタ DCR −0.13 Ω とドライバ RDS(on) 差) は数 % なので Resist は 4.4 Ω のまま動かしていません。換装で機体が 40.0 g → 36.3 g に軽くなったぶんは FF の Mass で受けています。

PWM 100 kHz と時間ディザ (DitherPwm)

PWM は 100 kHz (clk_sys 150 MHz で 1500 count ≈ 10.5 bit)。37.5 kHz から上げた際、低 DCR インダクタと組み合わせて 110 Hz のリミットサイクルが再発し、速度 PID の p/i を比率を保って下げることで解消しました (7 章)。

1 count 未満の duty は、PWM 周期ごとに compare 値を N / N+1 で切り替える 1 次誤差拡散で表現します。CPU は 1 kHz の制御周期ごとに次の 100 サンプル (+guard) を SRAM リングへ書くだけで、DMA が wrap ごとの DREQ で 1 周期 1 転送を ENDLESS + RING で永久に続けます。CPU が止まっても最後の duty が出続け、GPIO が High に張り付く経路がありません (詳細は docs/dither_pwm.md)。

吸引ランプ中の反動トルクは実測で −0.29° (ランプ最速の 1550〜1700 µs 帯)、終了時 +0.23° の戻りで、片側 duty 5 % ≈ 7 mN·m 相当です。走り出しの姿勢ずれの主因のひとつなので、2.8 節の start_align で吸収しています。

自作 ESC「ECia」: STM32G431KBU6 + MP6540HA によるセンサレス 6 ステップ ESC を esc/ECia/ で開発中です。デバッガと実機をつないだ HIL ループで、duty・時間・RPM を制限しながら段階的に進めています。本機の吸引には現時点では未搭載です。

IMU: ASM330LHH

車載グレードの 6 軸 IMU。SPI mode 3、ジャイロ ODR 3333 Hz / ±4000 dps、加速度 ±16 g。制御には Z 軸角速度だけを使い、DMA で 9 バイト (gz + ax/ay/az) をまとめて読みます。加速度は取り付け位置 (gyro_pos) の回転とレバーアーム補正を掛けたうえでログに出していますが、走行中の S/N 比が低く、自己位置推定への統合は保留中です。

エンコーダ: AS5147P ×2

14 bit の磁気式アブソリュートエンコーダ (SPI mode 1、28,000 rpm 対応)。生角度の上位 6 bit で 64 点の補正テーブルを引き、線形補間して 補正後 = 生角度 − table とします。テーブルは低速直進ログ (v ≈ 400 mm/s、置き直しながら 8〜11 本) から enc_lut_fit.py が左右差とジャイロだけで同定し、/enc_lut.hf として機体に送ります。同定した誤差は右 p-p 2.2° (1 次 0.92°)、左 p-p 0.93° で、直進の右輪速ノイズが −36 %、large 旋回の右輪速ノイズが −43 % になりました。磁石やタイヤを付け直したら取り直します。

困ったこと: 右エンコーダの磁石が外れかけていた期間があり、外輪になったときだけ生カウントが 1〜4 ms 停滞して速度推定が崩れ、両輪 100 % で膨らむ旋回が出ました (7 章)。

バッテリー電圧: ADS7042

12 bit SPI ADC (mode 0)。換算は V = battery_gain × 4 × raw / 4096 (battery_gain = 4.057)。LP 値を duty 計算の分母に使い、電圧が下がっても同じ電圧指令が出るようにしています。

SPI1 共有バス

ジャイロ (mode 3)、左右エンコーダ (mode 1)、バッテリー ADC (mode 0) が MISO=12 / CLK=14 / MOSI=15 を共有し、CS で切り替えます。ARM PL022 は CPOL/CPHA を変える前に SSE=0 が必要なので、spi_set_format_safe() (include/driver/spi_util.hpp) を必ず経由します。

1.7 基板・機構

基板写真・機構写真 (要提供)

本体 24.1 g + バッテリー 12.2 g。吸引でタイヤの潰れが変わるため、タイヤ径は吸引条件で測り直しています。足回りでは次の 2 件が制御に直結しました。

CHAPTER 2

制御

Core1 の 1 kHz IRQ で回る制御パイプラインを、推定 → 軌道生成 → フィードフォワード → フィードバック → 出力の順に説明します。ゲインの値は hardware.yaml / offset.yaml の 2026-09-25 時点のものです。

2.1 全体像: 1 kHz パイプライン

TIMER1 のアラーム 0 が 1 kHz で PlanningTask::tick() を呼び、次の順に処理します。SensingTask (TIMER0) が直前に更新したセンサー値を読み、tick の最後にモーター duty を確定します。

kim 座標系: 位置 KF はワールド座標のまま回しますが、制御が使う kim はセグメントごとの座標系で、旋回セグメントの遷移時に公称角 (last_tgt_angle) だけ回し直します。ワールド座標の増分をそのまま足すと 2 本目以降のセグメントで前進成分が横に漏れるため、増分を pos_θ − kim.θ ぶん逆回転してから加算します (2026-08-29 修正)。旋回中の角度誤差は i_bias = img_ang − kim.theta (計画角 − 実測角) で見ます。

予測入力に「前 tick の実測速度と今 tick の目標速度の差」を使っていた時期があり、目標と実測が乖離すると kf_v が負値まで発散する不具合がありました。予測入力を目標加速度に統一して解消しています。

エンコーダ・ジャイロの補正

  • 角度 LUT (1.4 節): 磁石の芯ずれとタイヤの振れによる 1 回転周期の誤差を 64 点テーブルで引きます。ログの v_l_enc / v_r_enc は補正前の生角度なので、補正の有無に関わらず再校正できます。
  • 実効トレッド: v_r − v_l = tread × w + (e_r − e_l) × v_c を最小二乗で解き、tread 42.32 mm と左右径差 −0.78 % を同定 (tread_check.py)。tread は旋回の差動 FF (Lm) のスケールに効きます。
  • 巡航速度の残差: 巡航中の v_c2 誤差の 85〜97 % は車輪回転の 3 次・4 次高調波で実運動ではなく、KF の調整では消えません。1 回転同期平均は 900 mm/s では −55 % 効きますが 2000 mm/s 以上では効果なしでした。
  • ジャイロゼロ点: 走行開始トリガー時に較正します。開始前に機体が傾いていると、その傾きごと「0°」になるので、後述の start_align と壁基準の姿勢推定 (wall_fit) で補います。

2.3 軌道生成

目標値の計算は MATLAB/Simulink でモデル化し、Embedded Coder で生成した gen_code_mpc/mpc_tgt_calc.cpp を組み込んでいます (tools/matlab_ws/)。毎 tick、前回の自分の出力 (ego_in) を起点に trj_length = 5 点先まで再計算する、実測を参照しないオープンループの自己伝播です。実測との差はすべて ControlLaw 側のフィードバックで吸収します。

直進

台形速度プロファイル。加速度は速度に応じた LUT (accl_v_x/y: 探索・最短・テストで別テーブル) で置き換え、壁誤差が大きいときは axel_degenerate テーブルで加速度を絞ります。減速はソフトスタート (1 − (1 − min(counter / decel_delay_cnt, 1))^decel_delay_n) で立ち上げます。この設定値が配線されておらず v > 5500 mm/s で減速が丸ごと消えるバグがありました (7 章)。

各 TurnType ごとに v / ang / rad / pow_n / front / back を持ち、角加速度の形状関数を pow_n で決めます。旋回ピークの角加速度・FF に必要な差動 duty・横 G は次の設計式で見積もれます (Lm 同定後に 136 件のプロファイルを監査した式)。

2.5 フィードバック

速度ループ (motor_pid2)

duty_c = p·e_v + i·∑e_v + b·(img_dist − dist_kf) + d·de_v/dt。帰還は v_kf (両輪 KF の平均)。現在値は p 8.5e-6 / i 3.0e-6 / d 8.75e-6 (b = 0)。PWM を 100 kHz にした際に 110 Hz のリミットサイクルが再発し、離散積分器が 110 Hz で P の 7 割を占めていたため p だけ下げても効かず、p と i を比率を保って下げることで解消しました。減速開始時 (加速度の符号反転) には I 項に ff_front_gain_decel を掛けて捨てます。

角速度ループ (gyro_pid)

目標 w_ref = ego_in.w + duty_roll_ang + sen_kanayama_dw (+ w_gain × i_bias) と実測 w_lp の差に対し、P (3.125e-4)、誤差和 b (2.15e-5)、角度差 i (0.01465、旋回前後と PIVOT でのみ有効)、D (2.95e-4) を効かせます。FF 主導なので P は極小です。

  • アンチワインドアップ: 誤差和と誤差が逆符号でデッドバンド (4.0 rad/s、壁制御中は ×10) を超えたらヒステリシス状態に入り、脱出時に ang.error_p / dt で再着火します。判定は 3 tick の debounce 付き (境界付近で毎 tick 反転し、1000 倍の再着火が繰り返されるチャタリングがあったため)。
  • 旋回の出入り: 旋回突入時に直進の誤差和を退避し、旋回終了時に 0 ではなくその値へ戻します (turn_end_w_i_restore: 1)。旋回中に貯めた値は捨てます。無条件に発火する旋回終了に error_p / dt の再着火を使うと残差の大きさに歯止めがなく、実機で不安定化しました。
  • 絶対値クランプ windup_i_max (現在 0 = 無効) も用意しています。同符号のまま単調に膨らむ暴走はヒステリシス条件では捕捉できません。

角度ループ (angle_pid) と壁 PD (str_ang_pid_fast)

直進では壁誤差 (両壁なら左右差、片壁なら基準との差 ×2、mm) を p 0.0375 / i 0.00375 / d 0.0325 で角度オフセット duty_sen [deg] にし、角度ループ (p 7.5 / d 4.5) が角速度の目標へ変換します。I 項は |誤差| > 15 mm で積算停止、積算値は ±0.09 でクランプします。角度ループの時定数は約 220 ms と遅く、旋回後の残差はこれだけでは戻らないため、旋回の制御則を直進へ引き継ぐ turn_settle (2.6 節) を入れました。

Kanayama カスケード: 壁誤差の P+D は速い (約 40 ms) が荒く、Kanayama 則 Δw = ky·ey + ki·∑ey + kθ·sin(eθ) は滑らか (約 240 ms) だが遅い。排他にせず並行実行し、速い立ち上がりを P+D、定常偏差と向きの調整を Kanayama が担います。現在値 ky 0.09 / ki 0 / kθ 1.0。eθ は kim.theta 基準です (ang_kf は現状計画値そのものなので使えない)。Kanayama の出力を計画側の ego_in.w に書き戻すと自己伝播で誤差が指数的に積もり左壁へ激突したため、1 tick 限りのオフセットとしてのみ加算します。

2.7 壁制御と壁切れ

壁誤差の作り方

45° センサーの mm 値から、両壁なら左右差、片壁なら基準距離 (sla_wall_ref 45 mm など) との差を 2 倍して誤差にします。壁の有無は exist しきい値 (46.5〜52 mm) で判定し、壁の切れ目 (kireme) 付近は誤差を 0 に落として姿勢を保ちます。探索の走り出しでは 22.5〜50 mm の区間で基準距離を再アンカーします。

壁切れ検知 (WallOffController)

最短走行の旋回位置は「壁が切れた位置 + 定数」で決めます。Core0 の WallOffController が旋回方向と壁の有無で戦略を選びます。

  • 壁あり開始: 注視側 45° の距離が noexist_th (49 mm) を超えたら壁切れ。基準は距離のレベル判定。
  • 壁なし開始 (柱の谷検知): 次の柱に近づいて読みが下がり、過ぎて急に遠のく「下に凸」の形を PillarTroughDetector (Core1、毎 tick) が追跡します。谷底が直前ピークより depth_min 8 mm 以上低く、谷底が 48〜80 mm の帯にあり、走行距離で正規化した 2 階微分 (曲率) が正で 2 tick 以上続いて合計 0.7 以上になったら離脱と判定。首振れや姿勢ドリフトは読みをほぼ直線に動かすので 2 階微分では符号が交互に振れるだけになり、1 階微分では紛らわしい緩い上昇を弾けます。発火位置ではなく谷底位置をアンカーにするので、発火までの遅れが補正定数に混ざりません。実機 8 本で 7 本が谷底 +1 tick で発火し、平均 lag は 4.53 → 1.71 mm になりました。
  • 安全網: 25 mm 通過の detect_pass_through_case2 と絶対しきい値の経路を残しています。以前は谷底が 60〜70 mm でばらついて絶対値判定を取りこぼし、安全網に落ちて旋回が 20 mm 遅れていました。
  • 斜め走行 (WALL_OFF_DIA): 対向の柱を 45° センサーで数え、dia*_offset で旋回ごとの補正上限を持ちます。

前壁補正 (FRONT_CTRL)

探索の突き当たりや超信地の前後で、前壁距離 (L90/R90 の平均) と左右差を専用 PID (front_ctrl_dist_pid / front_ctrl_angle_pid) で合わせます。基準は front_dist_offset 94.5 mm、超信地時は 90 mm。最短走行の SLA_FRONT_STR では前壁距離から旋回開始位置を補正し、距離が範囲外 (150 mm 超) のときは 180 mm のフォールバック値になるため、LP 値の丸めがログとずれて誤発火した件を四捨五入で直しています。

走行中の壁基準姿勢推定 (wall_fit)

ジャイロ座標系と迷路格子のずれ β [rad] を、走行方向 dy/dx = ang + β の 2 状態カルマン (y, β) で推定します。観測は z = lat − k·ang (45° センサーは回転だけで見かけの横位置が動くので k = 0.9 mm/deg を引く)。β は旋回をまたいでも不変なので走行全体で精密化でき、ang のスナップや start_align が ang を書き換えたときは β を同量逆に動かして整合を保ちます。

2.8 走り出しと停止

hold と吸引ランプ

走行開始前は hold() で機体を静止させながら吸引を立ち上げます。hold 中の角度積分は「動いたらリセット」方式 (0.15° で再基準化) です。ランプ完了後の待ちは固定時間ではなく、|kim_theta| (100 ms LPF) < 0.15° が 300 ms 続くまで (最短 100 ms、最長 500 ms、ランプ込みで 1200 ms 打ち切り)。ランプ中はファンの反動トルクで −0.29° 回り、プラトーに入ると +0.23° 戻ります。

start_align (走り出し姿勢リセット)

hold 中に 1〜2° 回ったまま走り出すと、ジャイロ積分の向きと迷路格子がずれたまま走ります。非探索の直進で壁を見ながら、走行距離 40 mm の窓で (走行距離, 壁横位置 − k·Δang) を最小二乗した勾配が 0.5° 未満・残差 0.3 mm 未満になったら、向きを 0 へ再アンカーします (zero_heading: 1)。1 区画の第 1 直線 (約 94 mm) では 1.8 m/s で判定が間に合わないため、80 mm 走ったら壁が見えた最初の tick で強制発火します (force_dist: 80)。ジャイロとの差が 90° 未満なら向きは触らず横位置だけ合わせる (apply_th: 90) 設定で、強制発火が旋回前の 0.3〜1.6° を捨てていた件を止めています。走り出し 360 mm までは壁の新規検出スナップも止めます。

n = 28 の走行で、走り出しの横位置と旋回開始時のヨーには −0.68 の相関 (0.8°/mm) があり、短い第 1 直線で壁 PD が最大 13° を指示して修正途中で旋回に入るのがばらつきの主因でした。手で押さえて走り出すと安定するので、hold の揺れ → 初期横ずれ → 旋回突入ヨー、の連鎖です。

2.9 モーター出力とフェイルセーフ

  1. summation_duty() がトルクを V に直し、左右の duty [%] を作る (FRONT_CTRL のみ専用の合成式)。
  2. apply_duty_limitter() で max_duty 99.95 % にクランプ。飽和した側と方向をログに残す。
  3. check_fail_safe() が duty / v / w / ang / wall_off の異常を fail_check のカウントしきい値で監視し、超えたら停止。
  4. MotorActuator::apply() が slow decay の 2 相 (駆動側 100 %、反対側 100 % − level) を Q16.16 で DitherPwm に渡し、左右を揃えて 1 回だけ update()。duty = 0 は両 H (ブレーキ)。
  5. 吸引は apply_us() が 32 bit ストア 1 回で DShot のフレーム語を差し替える。

2.5 節の図のとおり、gyro_pid や turn_end_brake の出力はトルク次元で、合成時に約 4600 倍されて duty% になります。ゲインの絶対値が小さく見えるのはこの前提です。

OS を使わず、2 コアとタイマー IRQ だけで組んだファームウェアの構造です。ビルドは Pico SDK 2.2.0 + GCC 15.2、C++20、-O3。

3.1 マルチコアと IRQ

  • コマンド受け渡し: Core0 の send_command() がバッファに書いて pending_cmd_idx_ を release 順序でセットし、Core1 は tick の先頭で acquire して取り込み、cp_request() でセグメントを切り替えます。
  • 起動・停止のラッチ: モーター有効化は Core0 が要求フラグを立て、Core1 が tick 内で KF リセット・軌道バッファ確保・PWM 有効化をまとめて行います。Core1 が毎 ms 触るデータとの競合を避けるためで、二重実行は ack フラグで防ぎます。
  • tick 同期: Core0 側の待ちは sleep_ms ではなく wait_tick() で Core1 の tick 進行に合わせます。
  • アラームの再アーム: フラッシュ書き込み中は Core1 が停止し、timer_hw->alarm への生書き込みと重なると SensingTask が恒久停止するレースがありました。目標時刻が過去なら INTF で強制発火させる arm_alarm32_safe() で回避しています。
  • IRQ 内ログ: irq_log のリングバッファに短いマーカーを積み、クラッシュ箇所の特定に使います。

3.2 SRAM 配置

RP2350 の XIP キャッシュは 16 KB なので、平均時間はフラッシュ上でも大きく変わりませんが、Core0 の printf や PSRAM アクセスでキャッシュが追い出されたときのジッタが制御ループに乗ります。対策として、ホットなコードとデータを SRAM に置きます。

  • 関数単位: __attribute__((noinline, section(".time_critical.<モジュール>"))) を IRQ ハンドラとホットパスに付与。
  • ファイル単位: memmap_custom.ld の .text / .rodata の EXCLUDE_FILE(...) に挙げたオブジェクトをフラッシュから除外し、.data 内で RAM に入れます。対象は src/planning/ src/action/ src/search/ src/utils/ src/logging/、SensingTask、UI、生成コード、センサー/PWM/DShot ドライバ、そこから呼ばれる SDK (pico_time、hardware_timer/spi/gpio/irq/dma/adc/pio)、libstdc++ の tree.o / hashtable、libc の malloc/free と mem*。printf / USB / LittleFS / cJSON / パラメータロードはフラッシュのまま。
  • SDK の float/double 実装は PICO_FLOAT_IN_RAM=1 / PICO_DOUBLE_IN_RAM=1。
  • 配置の確認は arm-none-eabi-nm -n build/ExiaIgnis.elf | awk '$1 ~ /^20/ && /veneer/' で、RAM 上のコードからフラッシュへの呼び出し (veneer) を列挙します。veneer を解決せずにコールグラフを見ると「0 件」と誤判定します。
領域サイズ備考

実測では配置の効果は −2〜−7 µs でレイアウトノイズ (±3〜5 µs) と同程度でした。tick 時間の増加の正体は DitherPwm (+40 µs) と trj_length 1 → 5 (13 → 66 µs) で、配置ではなく計算量です。ファイル単位配置の価値は「属性の付け忘れ監査が不要になる」保守性にあります。

3.3 起動シーケンス

  1. stdio_init_all()。直後に PSRAM の ID を素の状態で 1 回プローブ (結果は後でまとめて出力)。
  2. PlanningTask を生成して esc_.init() だけ先に実行。吸引 ESC は通電直後から有効な停止指令を期待するので、GPIO がフローティングのまま数秒経つと信号ロストのブザーが鳴り続ける。
  3. タクトスイッチ初期化。
  4. ConfigLoader::init() (LittleFS マウント、初回はフォーマット + デフォルト生成)。multicore_launch_core1 より前に行う。
  5. PSRAM 初期化 (sfe_setup_psram) と実書き込みテスト。失敗時はログ機能を無効化し、ダンプ時に dumperr 行を出す。
  6. LoggingTask 初期化 (PSRAM 先頭から最大 60,000 サンプル)。
  7. Core1 起動: flash_safe_execute_core_init() → SensingTask と PlanningTask の start_irq() → __wfi() ループ。
  8. MainTask: ブザー / UI 初期化 → パラメータロード → ボタン待ちループ (USB コマンド受付) → user_mode でテストモードか本走行へ。

MotionPlanning のポインタ設定 (setup_components()) より前に reset_tgt_data() / reset_ego_data() を呼ぶと null 参照で HardFault になるので、順序を固定しています。

CHAPTER 4

探索・経路生成

迷路の表現、足立法による探索、斜めを含む最短経路の生成と時間ベースの最適化をまとめます。実装は src/search/ と src/action/path_creator.cpp。

4.1 迷路マップ

map[x + y × maze_size] の 1 バイトにセルの情報を持ちます。ハーフサイズは maze_size: 32、ゴールは system.yaml の goals にセル座標のリストで与えます (左下原点)。

ビット意味
下位 4 bit (0x0f)壁の有無。North 0x01 / East 0x02 / West 0x04 / South 0x08
上位 4 bit (0xf0)踏破済みフラグ。North 0x10 / East 0x20 / West 0x40 / South 0x80。全方向踏破 = (map & 0xf0) == 0xf0

判定ヘルパーは existWall(x, y, dir) (壁あり)、isStep(x, y, dir) (その方向から踏み込んだことがある)、isProceed(x, y, dir) (壁なしかつ踏破済み)。探索結果は LittleFS の /maze.txt に保存し、片側探索・帰還探索は別ファイルに分けます。

4.2 足立法 (Adachi)

  • BFS で目的地からの歩数マップを作り、exec() が 1 歩ぶんの次移動方向 (Motion) を返します。
  • detect_next_direction() は前進方向を最優先し、左右は「歩数が低い同値でも更新しない」評価 (setNextDirection2) で判定、後退は enable_back の条件下のみ。
  • 未踏マスは subgoal_list にキャッシュし、ゴール到達後は帰還先を動的に切り替えます。
  • SearchMode は ALL (全探索) / Kata (片側探索) / Return (帰還探索)。探索時間は seach_timer 450 秒で、超えたら timeup_motion() で帰還します。

探索走行の速度は 425 mm/s (加減速 2500 mm/s²)、探索スラロームは Normal (v 300、rad 26)。探索中の壁切れ補正 (search_wall_off_*) と前壁補正 (front_dist_offset 94.5 mm) は 2 章の壁制御を探索用しきい値で使います。

4.3 ベクター距離マップ

斜め経路のコストは vector_map_t 配列に持ちます。n / e / w / s に各方向のコスト、N1 / NE / E1 / SE / S1 / SW / W1 / NW に 8 方向の通過カウントを格納し、updateVectorMap() が priority_queue で Dijkstra 的に更新します。Direction 列挙は North=1, East=2, NorthEast=3, West=4, NorthWest=5, SouthEast=6, SouthWest=7, South=8 で、now × dir == 8 が逆方向判定です。

4.5 時間ベースの経路最適化

timebase_path_create() は候補分岐マスを other_route_map に記録し、exec_param の 1〜5 パターンで path_create_with_change() を試して、calc_goal_time() (直線とスラロームのダミー実行で走行時間を積算) が最短の経路を path_set_map (priority_queue) から取ります。本走行モードには全プロファイルのタイムを計算するだけのサブモード (sim_run_time_all) があり、走らせる前にプロファイル間の比較ができます。

4.6 最短走行の構成

exec.json (YAML では run_prf.yaml) の各行が fast / normal / slow の 3 つのプロファイル番号を持ち、本走行モードの番号 2 以降がこれに対応します。path_run() はこの 3 つを ExecParamType (Fast / Normal / Slow) に割り当ててスラロームと直線のパラメータを読み、旋回ごとに違う速度を使い分けます。circuit_mode: 1 のときは迷路ではなく circuit.yaml のサーキットパスを走ります。

最短走行時の直線は速度に応じた加速度 LUT (accl_v_x/y) を使い、吸引なしのときは固定加速度に落とします。直線の最高速は vel_prof.yaml で 7,750 mm/s まで定義していますが、実測で確認しているのは 5.3 m/s までです (8 章)。

5.7 検証の作法

  • 制御変更の効果は単発比較ではなく n ≥ 4 の反復試行で判定する。ばらつきが 3σ で見込める場合は 1〜2 本で足りることもあるが、まずオフラインで当たりを付ける。
  • 「収束しない」と「duty が足りない」は別問題として切り分ける (平衡点が 0 か、飽和しているか)。
  • 壁切れの判定はしきい値ではなく形で行い、首振れとの分離は離脱の急峻さ・深さの数値で示す。
  • 失敗時の防御的コードは破棄だけで終わらせず、生データの保存と診断ログまで行う。
